# PrioritizeIdeas — методология и план разработки

Версия плана: 1.0 · 30.10.2026

Сервис для одной учебной команды из 4–8 человек. На занятии он помогает за 20–90 минут
пройти путь «каждый предложил → договорились о критериях → независимо оценили →
увидели согласие и споры → приняли решение». Первая версия поддерживает два типа этапов:
**Проблема** и **Идея**. Выбранная проблема переходит в этап идей.

---

## 0. Принятые решения и почему

| Решение | Почему |
|---|---|
| **Организатор всегда один (вы), ноутбук = «мозг» сессии.** Всё состояние хранится только в браузере ноутбука. | Ваш ответ. Это упрощает модель: один источник истины, нет конфликтов. |
| **Страница (только код) лежит на GitHub Pages. Участники открывают её по QR-коду.** | Ваш выбор (режим «В»). Свой сервер не нужен. |
| **Связь — через публичные бесплатные «почтовые ящики» (Nostr-релеи, запасной вариант — MQTT-брокеры). Все сообщения зашифрованы, ключ есть только в QR-коде.** Прямой WebRTC в первой версии **не используем**. | Изменение относительно обсуждения, причины ниже. |
| **Режим «Один экран» работает без всякой сети** (отдельный HTML-файл). | Страховка на случай, если сеть подведёт полностью. |
| Оценки по умолчанию **анонимны**, своё предложение оценивать **можно**, в настройках есть переключатель «не учитывать оценку автора». | Ваши ответы. |
| История — **черновики**: автоснимок на каждом этапе и экспорт проекта в файл. | Ваш ответ. |

### Почему не прямой WebRTC, а зашифрованная пересылка через релеи

Изначально я предлагал прямое соединение телефонов с ноутбуком (WebRTC), где посредник нужен
только для знакомства. Ресерч показал, что в вашей ситуации это самое ненадёжное место:

1. Без TURN-сервера (сервера-переправы) прямое соединение между разными сетями не
   устанавливается примерно в 20% случаев. Это оценка поставщика TURN-сервиса, своих измерений
   я не нашёл ([expressturn](https://blog.expressturn.com/webrtc-explained-simply)). В
   корпоративных и вузовских сетях часто стоит симметричный NAT и блокируется UDP
   ([Fora Soft](https://www.forasoft.com/learn/elearning-video/glossary/terms-elearning/turn-server),
   [addpipe](https://blog.addpipe.com/troubleshooting-webrtc-connection-issues/)).
2. Самый щедрый бесплатный TURN — у Cloudflare (1000 ГБ/мес,
   [Cloudflare](https://cloudflare.com/product/turn-sfu)). Но российские провайдеры с июня
   2025 года режут соединения с Cloudflare: после ~16 КБ данные перестают проходить
   ([Хабр](https://habr.com/ru/news/922532/), [Enterno](https://enterno.io/en/articles/cloudflare-in-russia)).
3. Фильтрация трафика, похожего на WebRTC, становится жёстче
   ([DEV](https://dev.to/andreik/otkazoustoichivyie-vidieozvonki-na-webrtc-cln)).
4. При этом данных у нас очень мало: 6 человек × 6 карточек × 4 критерия = 144 числа. Это
   единицы килобайт. Прямой канал нам не нужен.

**Вывод:** и ноутбук, и телефоны сами подключаются к нескольким публичным релеям по
обычному защищённому WebSocket (`wss://`, порт 443, как у любого сайта). Ноутбук и
телефоны не обязаны «видеть» друг друга, поэтому изоляция клиентов в вузовском Wi-Fi и NAT
нам не мешают. Сообщения шифруются (AES-GCM 256), ключ передаётся в части ссылки после
`#`. Эта часть ссылки не уходит ни на GitHub, ни на релеи. Релеи видят только
зашифрованные блоки и IP-адреса. **Честно:** это «посредник», но содержимого он не видит.
Если на этапе 0 окажется, что релеи в вашей сети работают плохо, а WebRTC работает,
транспорт можно поменять: он вынесен за отдельный интерфейс (раздел 6).

Про доступность GitHub Pages: с мая 2026 года у части российских пользователей GitHub
открывается нестабильно (~10–16% неудачных подключений), но Pages официально не
блокировали ([Meduza](https://meduza.io/news/2026/05/08/github-stal-ploho-otkryvatsya-v-rossii-roskomnadzor-utverzhdaet-chto-ne-blokiruet-ego),
[CNews](https://zoom.cnews.ru/soft/news/top/2026-07-14_rossiyane_poteryali_dostup/print)).
Защита от этого:
- **Кэширование для офлайна (PWA/Service Worker).** Кто хоть раз открыл страницу, дальше
  открывает её из кэша.
- **Зеркало** на втором бесплатном хостинге (GitLab Pages или Netlify). Какое именно —
  решим по результатам этапа 0.

## 1. Методология сессии (что происходит на занятии)

Каждый шаг опирается на исследование. Ниже указано, какую проблему шаг решает.

```
Лобби → Тихая генерация → Склейка дублей → Критерии → [Калибровка] → [Отбор]
      → Оценка → Раскрытие → [Спор и 2-й раунд] → Решение → Итог → (этап «Идея»)
```
Шаги в скобках необязательные: включаются в настройках или автоматически по правилам.

### Шаг 0. Настройка (на ноутбуке, около 1 минуты)
- Тип этапа: **Проблема** или **Идея**. Для «Идеи» выбирается исходная проблема из
  предыдущего этапа или вводится вручную.
- Сценарий времени (раздел 3). Таймеры мягкие, их можно продлить.
- Параметры:

| Параметр | По умолчанию |
|---|---|
| Анонимность авторов | Вкл |
| Лимит карточек на человека | 3 (диапазон 1–5) |
| Не учитывать оценку автора | Выкл |
| Калибровка | Вкл в «Стандарте» и «Паре» |
| Второй раунд | Вкл |

### Шаг 1. Лобби — подключение
- На экране ноутбука QR-код и кнопка «Скопировать ссылку», чтобы отправить её в чат команды.
- Участник сканирует код, вводит имя и попадает в комнату. Возле каждого имени индикатор связи 🟢/🟡/🔴.
- Вы тоже участник. Если ноутбук выведен на проектор, свои оценки удобнее ставить с телефона.
  Пульт организатора доступен и на ноутбуке.
- Опоздавшие могут подключиться на любом шаге.

### Шаг 2. Тихая генерация (метод номинальной группы)
**Проблема:** пока говорит один, остальные теряют свои идеи. Это основная причина, почему
групповой брейншторм проигрывает индивидуальной генерации
([Diehl & Stroebe 1987](https://www.uni-muenster.de/imperia/md/content/psyifp/aeechterhoff/wintersemester2011-12/seminarthemenfelderdersozialpsychologie/08_diehl_stoebe_productivityloss-brainstorming_jpsp1987.pdf)).
**Решение:** все пишут одновременно и молча, чужие карточки до конца шага скрыты.

**Карточка проблемы (шаблон):**

| Поле | Подсказка | Обязательно |
|---|---|---|
| Кто сталкивается | «студенты-первокурсники, живущие в общежитии» | да |
| В какой ситуации | «когда нужно…» | да |
| Что мешает | суть проблемы, 1–2 предложения | да |
| К чему приводит | последствие | нет |
| Откуда мы это знаем | Сам сталкивался / Видел у других / Есть данные / Догадка | да (выбор) |

Основание для полей: хорошая формулировка проблемы называет пользователя, контекст,
последствие и доказательства и не содержит решения
([шаблон](https://www.revisiondojo.com/student-faq/how-to-write-a-problem-statement),
[SAP AppHaus](https://apphaus.sap.com/resource/problem-statement-template)).

**Карточка идеи:**

| Поле | Подсказка | Обязательно |
|---|---|---|
| Название | 2–5 слов | да |
| Суть | что это, 1–2 предложения | да |
| Для кого | подставляется из «Кто сталкивается» выбранной проблемы, можно изменить | да |
| Как решает проблему | механизм | да |
| Чем пользуются сейчас | существующие альтернативы | нет |
| Откуда мы это знаем | те же 4 варианта | да (выбор) |

**Подсказки-проверки** (без ИИ, на правилах; не блокируют отправку, а советуют):
- Для проблемы: если в тексте есть «приложение», «сервис», «платформа», «сайт», «бот»,
  «создать», «сделать», появляется подсказка «Похоже на решение. Какая проблема за ним стоит?».
- «Кто» из одного слова («люди», «все», «студенты») → «Уточните, какие именно».
- «Что мешает» короче 25 символов → «Опишите конкретнее».
- Черновик карточки сохраняется на телефоне при каждом нажатии клавиши, поэтому не теряется при перезагрузке.

### Шаг 3. Склейка дублей
**Проблема:** трое написали одно и то же разными словами, голоса делятся между тремя карточками.
**Решение:** все карточки показываются анонимно на большом экране и на телефонах.
Организатор перетаскивает похожие карточки одну на другую. Объединённая карточка хранит
тексты всех исходных, все авторы считаются её авторами. Участники могут нажать «Это одно и
то же?» и предложить пару для склейки. Обсуждать можно только уточнения, критику оставляем
на потом. Отменить склейку можно до начала оценки.

### Шаг 4. Критерии
- Участники предлагают критерии со своих телефонов: из библиотеки (раздел 2) или свои.
  Организатор утверждает итоговый список.
- **У каждого критерия есть:** название, вопрос («Насколько больно тому, кто сталкивается?»),
  описания для оценок 1, 3 и 5, вес (1–3, по умолчанию 1), направление («больше — лучше» или
  «меньше — лучше», например «сложность»), метка (`новизна`, `реализуемость`, `ценность`,
  `проверяемость` или без метки).
- **Проверки:**
  - Больше 5 критериев → «Оценка займёт N×M кликов на человека. Оставьте 3–4».
  - Возможный дубль по словарю синонимов (актуальность ≈ востребованность ≈ важность;
    боль ≈ острота; частота ≈ регулярность; лёгкость ≈ реализуемость ≈ сложность (обратная))
    → «Эти критерии могут измерять одно и то же».
  - Критерий не подходит к типу этапа (например, «реализуемость» для проблемы) → предупреждение.
  - У своего критерия не заполнены описания для 1 и 5 → его нельзя утвердить. Описание для 3 необязательно.
  - Для этапа «Идея» без пары «новизна» + «реализуемость» → совет добавить её (нужна для матрицы, шаг 8).

Почему описания для 1/3/5 обязательны: шкалы с описанными уровнями повышают
согласованность оценщиков ([CLEERhub](https://stemedhub.org/groups/cleerhub/wiki/article:1256?action=pdf),
[DTIC](https://apps.dtic.mil/sti/pdfs/ADA142009.pdf)).

### Шаг 5. Калибровка (необязательно, около 2 минут)
Все оценивают одну **пробную** карточку по всем критериям. Пробная карточка берётся из
библиотеки или первой из предложенных, и её оценка в итог не идёт. Сервис показывает
разброс. Если по какому-то критерию оценки отличаются больше чем на 2 балла, критерий
подсвечивается: «Вы понимаете его по-разному — перечитайте описания 1/3/5 или поправьте их».
Это та самая «калибровка критериев», только сделанная за 2 минуты.

### Шаг 6. Отбор (автоматически, если карточек больше 6)
**Проблема:** усталость. 15 карточек × 4 критерия = 60 оценок на человека.
**Решение:** сначала голосование одобрением, отметки скрыты. Каждый отмечает до
`K = clamp(ceil(N/3), 2, 5)` карточек, где N — число карточек. Дальше проходят 5 карточек с
наибольшим числом отметок. Если на границе ничья, проходят все с равным счётом, но не больше 7.
Голосование одобрением простое и хорошо подходит для первичной фильтрации
([MITRE](https://stem.mitre.org/wp-content/uploads/2023/03/Voting_theory.pdf)). Если
карточек 6 или меньше, шаг пропускается.

### Шаг 7. Независимая (слепая) оценка
**Проблема:** якорение и конформность. Первый высказавшийся непропорционально влияет на
итог, а знание чужих оценок разрушает «мудрость толпы»
([PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC3107299),
[eScholarship](https://escholarship.org/uc/item/0qn7n21n)).
**Решение:**
- Каждый на своём телефоне оценивает каждую карточку-финалиста по каждому критерию:
  **5 кнопок 1–5** (кнопки удобнее ползунка на телефоне) или «Не могу оценить».
  Описания 1/3/5 видны прямо под вопросом.
- Карточки идут по одной («карусель»): удобно на телефоне и не даёт сравнивать с соседними.
  Порядок карточек у каждого участника свой, случайный, чтобы порядок не влиял на итог.
- У каждой карточки один раз отмечается **основание**: Опыт / Наблюдал / Данные / Догадка.
- Кнопка «Отправить» активна только после того, как заполнены все ячейки.
- Все видят только прогресс: «Аня ✓ · Петя ✓ · Олег 4/6 · …». Как кто проголосовал, не видно.
  **Анонимное содержание, но видимое участие:** так боремся с «социальной ленью»
  ([Faculty Focus](https://www.facultyfocus.com/articles/teaching-with-technology-articles/tips-addressing-loafing-group-projects/)).
- До раскрытия оценки можно менять.

### Шаг 8. Раскрытие результатов
Открывается, когда отправили все **или** когда организатор нажал «Раскрыть». Кворум — не
меньше половины активных участников. Карточка результата показывает:

1. **Итоговый балл 0–100** и место (формулы в разделе 4).
2. **Распределение по каждому критерию:** точки 1–5 без имён. Сразу видно «два лагеря» или «единогласно».
3. **Значки:**
   - 🤝 **Согласие** — разброс маленький, балл высокий.
   - ⚡ **Спорно** — оценки сильно расходятся (правила в разделе 4). Совет: «Обсудите, почему».
   - 💎 **Скрытый бриллиант** — не в топ-2, но лучшая по новизне или с сильными сторонниками.
     Люди систематически недооценивают оригинальное в пользу реализуемого
     ([обзор Mueller et al. 2011](https://journalistsresource.org/economics/bias-against-creativity-ideas/)).
   - 🎲 **На догадках** — больше половины оснований = «Догадка». Совет: «Проверьте опросом».
     Здесь пригодится ваш критерий «доступность людей».
4. **Матрица 2×2.** По умолчанию: для проблем — «Боль × Частота», для идей — «Реализуемость × Новизна».
   Оси можно выбрать из любых двух критериев.
5. **Прозрачность балла:** нажатие на балл показывает расчёт: средние по критериям × веса → итог.
6. **Устойчивость лидера:** «Лидер не меняется, если убрать любой один критерий или любого
   одного участника» ✅ или «Лидер неустойчив: без критерия X первое место у карточки Y» ⚠️.

### Шаг 9. Обсуждение спорных и второй раунд (метод Дельфи)
**Проблема:** после обсуждения люди меняют мнение, но таблица уже заполнена.
**Решение:**
- По каждой карточке со значком ⚡ запускается обсуждение с таймером на 2 минуты. Подсказка
  для ведущего: «Пусть по одному человеку из каждого лагеря скажет, почему».
- Любой может анонимно добавить **аргумент** («за» или «против»), он сохраняется в истории.
  Так появляются аргументы меньшинства.
- **Второй раунд:** переоценка **только спорных** карточек, вслепую. После раскрытия видно,
  как сдвинулись оценки: «Разброс по “Боли” сократился с 3 до 1».
- Основание: в экспериментах RAND анонимная обратная связь со вторым раундом чаще повышала
  точность, а очное обсуждение чаще её снижало
  ([RAND/DTIC](https://apps.dtic.mil/sti/pdfs/AD0690498.pdf)).

### Шаг 10. Решение
Организатор помечает каждую карточку одним статусом:
- ✅ **Выбрано** (одна или несколько) — поле «Почему выбрали» (одна строка, можно пропустить).
- ⏸ **Отложено** — «вернуться позже», причина обязательна. Сюда же автоматически
  предлагаются 💎 и ⚡ карточки, которые проиграли.
- ✖ **Отклонено** — причина по желанию.

Итоговое решение принимает команда. Сервис только подсвечивает и предупреждает: если
выбрана не лидирующая по баллу карточка, он просит одну строку «почему». Это нормально,
просто фиксируем причину.

### Шаг 11. Итог и экспорт
- **Страница итога:** выбранное, альтернативы, критерии с весами, таблица баллов, значки,
  аргументы, отложенное с причинами, участники (без авторства, если включена анонимность).
- **Экспорт:**
  1. **«Для Lean Canvas»** — готовый текст для полей канваса, кнопка «Скопировать»:
     - *Problem* — выбранные проблемы и до двух отложенных;
     - *Customer Segments* — поля «Кто сталкивается»;
     - *Existing Alternatives* — поля «Чем пользуются сейчас» из идей;
     - *Solution* — суть выбранной идеи;
     - *Unique Value Proposition* — черновик из «Как решает проблему»;
     - остальные поля пустые, с подсказкой.
  2. **Печать / PDF** через печать браузера (отдельная вёрстка для печати).
  3. **Markdown** (`.md`) — для чата команды или отчёта.
  4. **Файл проекта** (`.json`) — полная резервная копия, можно импортировать обратно.
- Кнопка **«Перейти к идеям»** создаёт этап «Идея», в котором выбранная проблема уже указана как исходная.

## 2. Библиотека критериев (стартовая)

Шкала везде 1–5. Для каждого критерия указаны описания уровней 1 / 3 / 5.

**Для проблем**

| Критерий | 1 | 3 | 5 | Метка |
|---|---|---|---|---|
| Боль | Лёгкое неудобство, легко игнорировать | Заметно мешает, иногда ищут обходные пути | Сильно мешает, люди активно ищут решение или тратят деньги/время | ценность |
| Частота | Раз в год и реже | Раз в месяц | Каждый день или неделю | ценность |
| Масштаб | Единицы людей | Заметная группа (поток, факультет) | Массовая (все студенты города и шире) | ценность |
| Доступность людей для опроса | Не знаем, где найти, не дотянемся | Найдём с усилием (знакомые знакомых) | Они рядом — одногруппники, соседи, можно опросить на этой неделе | проверяемость |
| Проверяемость | Непонятно, как проверить, что проблема есть | Можно проверить опросом | Можно проверить фактами или наблюдением быстро | проверяемость |
| Слабость текущих решений | Уже есть хорошие решения | Решения есть, но с явными минусами | Решений нет или все плохие | ценность |
| Близость команде | Никто в теме не разбирается | Кто-то сталкивался | Мы сами — целевая аудитория или эксперты | реализуемость* |

\* «Близость команде» — единственный «реализуемостный» критерий, уместный для проблем. Для
него не показывается предупреждение о несоответствии типу этапа.

**Для идей**

| Критерий | 1 | 3 | 5 | Метка |
|---|---|---|---|---|
| Новизна | Копия существующего | Известное в новом контексте | Аналогов не знаем | новизна |
| Реализуемость за курс | Нужны годы, деньги или команда профи | Сложно, но MVP возможен | Прототип можно сделать за 1–2 недели | реализуемость |
| Ценность для пользователя | «Приятно, но не нужно» | Заметно помогает | Решает боль полностью | ценность |
| Отличие от альтернатив | Не лучше текущих | Лучше в одном аспекте | Явно лучше по главному параметру | новизна |
| Проверяемость гипотезы | Не проверить без готового продукта | Проверим опросом или макетом | Проверим быстрым экспериментом на людях | проверяемость |
| Монетизация | Непонятно, кто заплатит | Есть идея модели | Понятно кто, за что и сколько | ценность |

Библиотека редактируется. Свои критерии сохраняются на ноутбуке и предлагаются в следующих сессиях.

## 4. Математика (точные правила)

Обозначения: r — оценка участника p по карточке i и критерию c, число от 1 до 5 или «нет».

1. **Направление.** Для критериев «меньше — лучше» оценка переворачивается: r' = 6 − r.
2. **Исключения.** Не учитываются ответы «Не могу оценить». Если включено «Не учитывать
   оценку автора», не учитываются и оценки авторов карточки (у склеенной — всех её авторов).
3. **Среднее по критерию:** m(i,c) = среднее учтённых r'. Если учтённых оценок меньше 2, у
   балла пометка «мало оценок».
4. **Итоговый балл:** S(i) = Σ w(c)·m(i,c) / Σ w(c), а затем **0–100**: (S − 1) / 4 × 100,
   округление до целого. Медиана показывается рядом, но не участвует в ранжировании: при 4–6
   людях и шкале 1–5 медиана даёт слишком много ничьих.
5. **Спорность** считается по каждому критерию при n ≥ 3. Значок ⚡ ставится, если
   *размах* (max − min) ≥ 3 **или** есть хотя бы одна оценка ≤ 2 и хотя бы одна ≥ 4, и при этом
   стандартное отклонение ≥ 1,2. Карточка спорная, если спорен хотя бы один критерий с весом ≥ 1.
6. **Согласие** 🤝: балл ≥ 70 и ни один критерий не спорный.
7. **Скрытый бриллиант** 💎: карточка не в топ-2 по баллу и выполняется одно из условий:
   (а) максимальное среднее по критерию с меткой `новизна` среди всех карточек;
   (б) хотя бы два участника поставили 5 по критерию с меткой `ценность`, и карточка спорная.
8. **На догадках** 🎲: доля «Догадка» среди оснований этой карточки больше 50%.
9. **Ничья:** баллы различаются не больше чем на 2. Порядок разрешения: меньше спорных
   критериев → больше отметок на шаге «Отбор» → решает организатор (с пометкой «ничья»).
10. **Устойчивость лидера:** пересчёт без каждого критерия по очереди и без каждого
    участника по очереди. Если хоть в одном пересчёте лидер другой, ставится ⚠️ с объяснением.
11. **Второй раунд** заменяет оценки первого раунда только по спорным карточкам. Первый раунд
    сохраняется в истории для отчёта «как сдвинулись».

Всё это реализуется чистыми функциями и покрывается тестами с ручными примерами (раздел 9).

## 5. Архитектура

```
┌────────────────────────────────────────────┐
│ GitHub Pages (+ зеркало)                   │  ← только статический код (HTML/JS/CSS)
└───────────────┬────────────────────────────┘
                │ первая загрузка, потом кэш (Service Worker)

   │ • расчёты, история      │        │ • отправка действий      │
   │ • IndexedDB (проекты)   │        │ • localStorage (черновик)│
   └───────┬─────────────────┘        └───────────┬──────────────┘
           │   зашифрованные сообщения (AES-GCM)  │
           └─────────►  2–3 публичных релея  ◄────┘
                    (Nostr wss:443; запасные MQTT wss)
```

- **Стек:** TypeScript + Vite (сборка) + Preact + @preact/signals (интерфейс и состояние,
  ~10 КБ) + nostr-tools (релеи Nostr) + mqtt.js (запасной транспорт) + qrcode-generator (QR) +
  собственные SVG-графики без тяжёлых библиотек. Тесты: Vitest и Playwright.
  Почему так: всё работает в браузере, ничего не нужно устанавливать, сборка — несколько
  статических файлов, страница лёгкая и быстро грузится по мобильному интернету.
- **Версии зависимостей:** фиксируются точно (без `^`). Берётся выпуск старше 14 дней, проверка через `npm view <пакет> time`.
  Уже проверено: `trystero 0.26.0` (04.10.2026) — на случай, если понадобится WebRTC.
- **Две сборки:**
  1. `web` — для GitHub Pages, с сетью, PWA, офлайн-кэшем.
  2. `single` — один файл `PrioritizeIdeas-offline.html` (через `vite-plugin-singlefile`).
     Работает при открытии двойным кликом, без сети, только режим «Один экран».
- **Хранение у организатора:** IndexedDB (проекты, этапы, снимки) + кнопка экспорта `.json`.
  Ключи с префиксом `pi:`: все сайты `<имя>.github.io` делят одно хранилище браузера.
- **Хранение у участника:** localStorage — id участника, имя, черновики карточек, неотправленные
  оценки, ключ комнаты. Так перезагрузка страницы ничего не ломает.
- **Ноутбук не засыпает:** Screen Wake Lock API, пока идёт сессия, плюс подсказка
  «Подключите зарядку» при старте.

## 6. Протокол обмена

### Комната и ключ
- Организатор создаёт `roomId` (16 случайных байт) и `key` (32 случайных байта, AES-GCM).
- Ссылка в QR-коде: `https://<user>.github.io/prioritize/#j=<roomId>.<key>` (base64url).
  Часть после `#` браузер никуда не отправляет.
- Тема/тег на релее: `sha256("pi:" + roomId)` — первые 16 символов. Так по теме не узнать roomId.

### Транспортный интерфейс
```ts
interface Transport {
  connect(room: RoomInfo): Promise<void>
  send(msg: Envelope): Promise<void>        // широковещательно в комнату
  onMessage(cb: (msg: Envelope) => void): void
  status(): 'online' | 'degraded' | 'offline'
  close(): void
}
```
Реализации:
- `NostrTransport` — основной. Эфемерные события (kind 20000–29999), они не хранятся на релее;
  фильтр по тегу комнаты; одноразовая пара ключей на сессию. Отправка идёт **сразу в 2–3
  релея**, получатель отбрасывает дубли по `(from, seq)`.
- `MqttTransport` — запасной (broker по wss). Включается, если Nostr недоступен.
- `LocalTransport` — режим «Один экран» и тесты (всё в одной вкладке).
- `TrysteroTransport` — в резерве. Подключаем, если этап 0 покажет, что WebRTC работает лучше релеев.

### Конверт сообщения
```ts
type Envelope = {
  v: 1,                 // версия протокола
  from: string,         // id отправителя (случайный, хранится в localStorage)
  seq: number,          // возрастающий номер сообщения отправителя
  t: number,            // время отправителя, мс
  type: string,
  body: unknown
}
// в сеть уходит: base64( iv(12 байт) || AES-GCM(JSON(Envelope)) )
```
- Сообщения больше 12 КБ режутся на части (`chunk i/n`) и собираются на стороне получателя.
  Причина: ограничения релеев на размер и поведение сетей, которые режут длинные соединения.
- Подтверждения: на каждое действие участника организатор отвечает `ack(from, seq)`. Если
  подтверждения нет 3 секунды, отправка повторяется (до 5 раз), потом статус «нет связи».

### Типы сообщений
| От участника | Назначение |
|---|---|
| `hello {pid, name}` | вход или повторное подключение |
| `card.upsert / card.delete` | карточка (id создаёт сам участник) |
| `merge.suggest {a, b}` | «это одно и то же?» |
| `criterion.propose` | предложить критерий |
| `calib.submit`, `approve.submit`, `rate.submit {round}` | оценки целиком, не по одной (идемпотентно) |
| `arg.add {cardId, side, text}` | аргумент на обсуждении |
| `resync.request {sinceVersion}` | «я что-то пропустил» |

| От организатора | Назначение |
|---|---|
| `state {version, phase, deadline, hostTime, publicState}` | общее состояние (одно для всех) |
| `ack {to, seq}` | подтверждение |

### Как соблюдается «слепота» без личных сообщений
Организатор рассылает **одно общее** состояние. До раскрытия в нём **нет** чужих оценок,
только прогресс («отправил / сколько заполнил»). Свои оценки участник держит у себя и видит
их локально. После раскрытия в общее состояние попадают оценки, привязанные к
**псевдонимам** («Участник 3»), а не к именам. Авторство карточек в общем состоянии скрыто:
участник узнаёт свои карточки, потому что сам создавал их id. Исключение «оценки автора»
считает организатор, ему связь известна.
**Честно:** ноутбук организатора технически знает, кто что поставил. Интерфейс это не
показывает, при включённой анонимности в экспорт это не попадает.

### Обрывы связи
- Телефон ушёл в фон или выключил экран (особенно iOS) → по `visibilitychange` и `online`
  он переподключается и шлёт `resync.request`.
- Организатор на каждое изменение повышает `version`. Если участник видит пропуск версии,
  он запрашивает полное состояние.
- Ноутбук перезагрузился или вкладку закрыли → состояние восстанавливается из IndexedDB,
  комната та же, участники подключаются сами.
- Время: таймер у всех считается от `deadline` организатора с поправкой
  `hostTime − localTime`, поэтому неточные часы телефонов не мешают.

## 7. Экраны

**Организатор (ноутбук):**
1. Проекты — список, черновики (снимки), импорт и экспорт.
2. Новый этап — тип, сценарий, параметры.
3. Лобби — QR, ссылка, участники и индикаторы связи.
4. Пульт шага — таймер, прогресс, кнопки «Дальше / Назад / +2 мин / Раскрыть».
5. Большой экран (режим проектора) — крупный шрифт, без пульта и без личных данных.
6. Склейка — перетаскивание карточек.
7. Критерии — библиотека, редактор описаний 1/3/5, проверки.
8. Результаты — рейтинг, распределения, значки, матрица 2×2, устойчивость.
9. Решение и итог — статусы, причины, экспорт.
10. Диагностика — состояние релеев, задержки, журнал (кнопка «Скопировать отчёт»).
11. Настройки — релеи, зеркало, библиотека критериев.

**Участник (телефон, от 360 px в ширину):**
Вход (имя) → Ожидание → Мои карточки → Все карточки (на склейке) → Предложить критерий →
Калибровка → Отбор → Оценка (карусель) → Результаты → Обсуждение (аргументы) → Итог.

Общие требования: кнопки не меньше 44 px, светлая и тёмная темы, русский язык с правильными
склонениями («1 карточка, 2 карточки, 5 карточек»), никакой горизонтальной прокрутки.

**Режим «Один экран»:** те же шаги, но участники по очереди. Ноутбук передаётся с
экраном-заглушкой «Передайте Ане — нажмите, когда она у экрана», и чужие оценки не видны.

## 8. Модель данных

```ts
Project   { id, title, createdAt, updatedAt, stages: Stage[] }
Stage     { id, type: 'problem'|'idea', sourceCardIds: string[], settings: Settings,
            phase: Phase, deadline?: number, participants: Participant[],
            cards: Card[], criteria: Criterion[], calibration?: Rating[],
            approvals: Approval[], ratings: Rating[], args: Arg[],
            decisions: Decision[], snapshots: Snapshot[] }
Participant { id, name, alias: string /*"Участник 3"*/, joinedAt, active: boolean, lastSeen }
Card      { id, authorIds: string[], fields: Record<string,string>, basis?: Basis,
            mergedFrom: string[], createdAt }
Criterion { id, name, question, anchors: {1:string, 3?:string, 5:string},
            weight: 1|2|3, inverted: boolean, tag?: Tag, fromLibrary?: string }
Rating    { raterId, cardId, criterionId, value: 1|2|3|4|5|null, round: 1|2 }
Basis     'experience'|'observed'|'data'|'guess'   // одно на (raterId, cardId)
Approval  { raterId, cardIds: string[] }
Arg       { id, cardId, side: 'pro'|'con', text, createdAt }   // без автора
Decision  { cardId, status: 'chosen'|'deferred'|'rejected', reason?: string }
Snapshot  { id, at, phase, data: Stage /*копия*/ }
Phase     'lobby'|'generate'|'merge'|'criteria'|'calibrate'|'shortlist'
          |'rate'|'reveal'|'discuss'|'rate2'|'decide'|'summary'
```

**Правила переходов:**
- «Назад» разрешено до начала оценки.
- Изменение критериев после начала оценки удаляет оценки по этому критерию, но сначала
  показывается подтверждение.
- Снимок (черновик) сохраняется автоматически при каждом переходе вперёд.
- «Восстановить черновик» создаёт **новый** этап из снимка и ничего не затирает.

## 9. Тестирование

1. **Модульные тесты (Vitest):** вся математика раздела 4 на таблицах-примерах, посчитанных
   вручную, включая крайние случаи (1 участник, все «не могу», ничья, авторские исключения,
   перевёрнутые критерии); проверки-подсказки; разрешённые и запрещённые переходы машины состояний.
2. **Протокол:** дубли, потери, сообщения не по порядку, сборка частей, повтор без
   подтверждения. Для этого есть искусственный транспорт, который теряет и перемешивает сообщения.
3. **Сквозные тесты (Playwright):** 1 организатор + 6 участников в отдельных контекстах
   браузера проходят полный цикл «Проблема → Идея». Отдельно — сценарии «участник
   перезагрузил страницу», «организатор перезагрузил страницу», «участник опоздал».
4. **Устройства для ручной проверки:** Chrome (Android), Safari (iOS 16+), Яндекс Браузер
   (Android), Chrome и Edge на ноутбуке.
5. **Полевой тест** на настоящем занятии (этап 5).

## 10. План работ по этапам

Каждый этап заканчивается контрольной точкой: вы что-то проверяете, и только потом идём дальше.

### Этап 0. Сетевой тест — снимаем главный риск
- Маленькая страница на GitHub Pages:
  - открывается ли сам github.io;
  - подключение к 6–8 Nostr-релеям и 3 MQTT-брокерам по wss;
  - **проверка устойчивости:** 60 сообщений по 1 КБ туда и обратно между двумя устройствами
    (ловим «обрезание после 16 КБ» у релеев за Cloudflare);
  - задержка;
  - для сравнения — WebRTC через Trystero.
- Результат — таблица и кнопка «Скопировать отчёт».
- **Контрольная точка:** на паре 2–3 человека запускают тест в вузовском Wi-Fi и через
  мобильный интернет, вы присылаете отчёты. По ним я фиксирую список релеев, основной
  транспорт и зеркало.

### Этап 1. Ядро без сети
- Каркас проекта, модель данных, машина состояний, вся математика с тестами, хранение в IndexedDB.
- Режим «Один экран»: полный цикл этапа «Проблема» на одном ноутбуке.
- Сборка `single`: один HTML-файл.
- **Контрольная точка:** вы проходите сессию на ноутбуке (можно одному за нескольких
  «участников») и говорите, что неудобно.

### Этап 2. Сеть
- Транспорт по результатам этапа 0, шифрование, вход по QR, лобби, подтверждения,
  переподключение, блокировка сна.
- «Слепое» общее состояние, прогресс участников.
- Сборка `web`, развёртывание на GitHub Pages через GitHub Actions, Service Worker, зеркало.

## 11. Риски и что с ними делаем

| Риск | Вероятность | Что делаем |
|---|---|---|
| Релеи недоступны в вузовской сети или режут длинные соединения | средняя | Этап 0, несколько релеев одновременно, MQTT как запасной транспорт, «Один экран» |
| github.io не открывается у части людей | низкая–средняя | Кэш PWA, зеркало, ссылку можно открыть через мобильный интернет |
| Публичный релей закрылся или ввёл ограничения | средняя (со временем) | Список релеев в настройках, автоматический отбор живых при старте |
| iOS обрывает соединение в фоне | высокая | Переподключение и запрос полного состояния, черновики хранятся локально |
| Ноутбук уснул или сел | средняя | Блокировка сна, напоминание о зарядке, восстановление из IndexedDB |
| Участник открыл ссылку на втором устройстве | средняя | Вход по имени: «Вы уже в комнате на другом устройстве — продолжить здесь?» |
| Фото QR попало к посторонним | низкая | Ключ действует только в этой сессии; кнопка «Новый ключ» перевыпускает QR и пускает участников заново |
| Команда больше 8 человек | низкая | Общее состояние одно для всех, нагрузка почти не растёт; интерфейс проверим на 10 участниках |
| Обсуждение затягивается | высокая | Мягкие таймеры, «Экспресс» без второго раунда, обсуждаются только ⚡ карточки |
