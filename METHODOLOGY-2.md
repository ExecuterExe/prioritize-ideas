## 0. Коротко

1. **Всё строим на одном фундаменте — конструкторе.** Сейчас в коде зашиты два типа
   карточек: «Проблема» и «Идея». Их заменяют **шаблоны этапов** с настраиваемыми полями.
   Тогда почти все остальные идеи — это готовые шаблоны и два новых режима этапа, а не
   отдельные подсистемы.
2. **Берём 8 идей из 10, но в разной глубине.** Две урезаем осознанно:
   - распределение ресурсов сводим к «кто и к какому сроку проверяет», без
     полноценного планировщика;
   - во вложениях файлов отказываем, вместо них — ссылки.
3. **Порядок внедрения:**
   - конструктор;
   - паспорт задания;
   - реестр предположений вместе с экспериментами;
   - развитие идей;
   - pre-mortem;
   - карта пути;
   - сценарии «что если»;
   - MVP-доска.
4. **Главное ограничение, о котором текст молчит:** «сервер» — ваш ноутбук. Между
   занятиями участники не видят проект. Механики «на несколько недель» (эксперименты,
   задачи) работают только во время сессий плюс через экспорт в чат команды. Это
   нужно принять осознанно (вопрос 1 в разделе 11).

## 1. Разбор предложенного текста

### Что в тексте сильно
- **Верный принцип:** «не навязывать методологию, а дать инструменты собрать свою».
  Он прямо ложится на нашу архитектуру: движок этапа уже отделён от содержимого карточек.
- **Сквозная связь «проблема → идея → предположение → эксперимент»** — это то, чего
  нет ни в Google-формах, ни в простых голосовалках.
- **Методики реальные:** Design Sprint, pre-mortem Гэри Кляйна, карта предположений
  Дэвида Бланда, 1-2-4-All из Liberating Structures. Их можно опереть на источники
  (раздел 10).

### Что в тексте спорно
| Замечание | Почему важно | Что делаем |
|---|---|---|
| Уклон в «рабочую среду на недели» (ресурсы, MVP, задачи) | Наш сценарий — занятие на 20–90 минут и телефоны. Планировщик ресурсов на телефоне на паре — это уже Jira, текст сам предупреждает, что ею быть не надо | Каждая механика должна укладываться в один шаг сессии на 5–15 минут. Долгие механики — только в виде «паспорта» результата |
| Поле «прикрепление файла» | Сообщения идут через публичные релеи небольшими порциями. Файлы раздувают состояние и упираются в лимиты | Только поле «ссылка» |
| Генеалогия идей «с авторами» | Противоречит анонимности: по дереву «кто развил чью идею» вычисляется авторство | При включённой анонимности в дереве номера карточек, а не люди |
| Условные поля, связи, шаблоны — «всё сразу» | Сложный конструктор отпугнёт: большинство никогда не будет собирать шаблон | Готовые сценарии по умолчанию, конструктор — для тех, кому нужно |
| Оценки «9/10, 10/10» у всех идей | Это самооценка автора текста, по ней нельзя расставлять порядок | Порядок задаём по зависимостям и стоимости (раздел 9) |
| «30% лучше находят причины» (популярный пересказ про pre-mortem) | В исходном исследовании 1989 года, судя по разборам, измеряли *количество* названных причин, а не их точность | В подсказках интерфейса не обещаем цифр |

## 2. Принципы, по которым встраиваем

1. **Ядро не трогаем.** Слепая оценка, карта разногласий, калибровка и второй раунд
   работают для любого шаблона без изменений.
2. **Новое — данные, а не код.** Новая методика = новый шаблон и, если нужно, один из
   немногих режимов этапа. Отдельные экраны пишем только там, где без них нельзя.
3. **Одна механика — один шаг на 5–15 минут.** У каждого режима есть тайминги
   «Экспресс» и «Стандарт».
4. **По умолчанию — готовое.** Новый проект предлагает сценарий из библиотеки.
   Конструктор открывается кнопкой «Настроить».
5. **Анонимность сильнее красоты.** Если механика выдаёт авторство, при анонимности
   она показывает номера, а не имена.
6. **Телефон — главный экран участника.** Поле, неудобное на телефоне, в шаблон не
   попадает или упрощается (дата — обычный выбор, мультивыбор — кнопки-чипы).
7. **Обратная совместимость.** Старые проекты с этапами «Проблема» и «Идея» открываются
   и выглядят так же: они становятся встроенными шаблонами.

## 3. Фундамент: конструктор (идея 1)

### 3.1. Понятия

```
Проект
 ├─ Паспорт задания                     (один на проект)
 ├─ Сценарий: цепочка этапов             Карта пути → Проблема → Идея → Предположения → Эксперимент
 ├─ Этапы
 │   └─ Этап = Шаблон этапа + режим + карточки + оценки
 │        └─ Шаблон этапа = тип карточки (поля) + критерии по умолчанию + тексты подсказок
 └─ Реестры проекта: Предположения, Эксперименты, Риски
```

- **Тип карточки** — набор полей: какие данные собирает участник.
- **Режим этапа** — как идёт работа. Режимов немного:
  - `decide` — сбор → оценка → решение (текущий процесс);
  - `journey` — карта пути;
  - `board` — доска компонентов MVP.
- **Шаблон этапа** = тип карточки + режим + стартовые критерии + подсказки + что
  передаётся дальше.
- **Сценарий** — сохранённая цепочка шаблонов этапов.

### 3.2. Типы полей

| Тип | Как выглядит на телефоне | Проверки |
|---|---|---|
| `text` (короткий текст) | строка | длина до 200 |
| `longtext` (длинный текст) | многострочное поле | длина до 600 |
| `number` (число) | цифровая клавиатура | мин./макс. |
| `percent` (процент) | число со знаком % | 0–100 |
| `select` (выбор одного) | кнопки-чипы, если вариантов ≤ 5, иначе список | один из вариантов |
| `multiselect` (выбор нескольких) | кнопки-чипы | только из вариантов, лимит |
| `checkbox` (флажок) | переключатель | — |
| `date` (дата) | системный выбор даты | — |
| `scale` (шкала 1–5) | 5 цветных кнопок, как в оценке | 1–5 |
| `link` (ссылка) | строка | http(s)-адрес |
| `cardref` (связь с карточкой) | выбор из карточек проекта | id существует |

**Вложения файлов не поддерживаем:** через релеи данные идут небольшими порциями, а
файл на ноутбуке организатора другие участники всё равно не увидят. Вместо файла —
поле «ссылка» (Google Диск, Яндекс Диск).

**Свойства любого поля:**
- `required` — обязательное;
- `hint` — подсказка-пример;
- `showIf` — условие показа: `{field, equals | in | notEmpty}`.

Пример условного поля: поле «Источник доказательства» видно, только если
«Основание = Есть данные».

**Ещё в типе карточки:**
- `titleField` — какое поле считается заголовком;
- `subtitleFields` — какие поля показываются подзаголовком;
- `lint` — подсказки-проверки из библиотеки правил: `solution-words`, `vague-who`, `too-short`.

### 3.3. Передача между этапами
У шаблона этапа есть «вход». Выбранные карточки предыдущего этапа становятся контекстом
(как сейчас «Проблема:» в этапе идей), а поля можно подставить заранее:
```
prefill: { who: 'source.who', context: 'source.what' }
```
В интерфейсе это строка в редакторе поля: «Подставлять из предыдущего этапа:
[поле ▾]». Так «Для кого» в идее само подтягивается из «Кто сталкивается» в проблеме.

### 3.4. Редактор шаблона (для организатора)
- Слева список полей: перетаскивание, «+ Поле», выбор типа. Справа —
  **живой предпросмотр в рамке телефона**: организатор сразу видит, что получит участник.
- У каждого поля: название, подсказка, обязательность, варианты (для выбора),
  «показывать, если…», «подставлять из…».
- **Проверки качества самого шаблона:**
  - больше 6 обязательных полей → «на телефоне это 3+ экрана, сократите»;
  - нет поля-заголовка → нельзя сохранить;
  - условие ссылается на удалённое поле → ошибка.
- **Сохранение:** «Мои шаблоны» хранятся на ноутбуке. Шаблон экспортируется в `.json`:
  его можно отправить одногруппникам, а преподаватель может раздать свой.
- **Блокировка:** после начала генерации шаблон этапа нельзя менять. Этап хранит копию
  шаблона, поэтому правка шаблона в библиотеке не ломает прошлые этапы.

### 3.5. Встроенная библиотека сценариев
| Сценарий | Цепочка | Когда |
|---|---|---|
| Классика (как сейчас) | Проблема → Идея | «Придумайте проблему и решение» |
| Sprint-lite | Карта пути → Проблема → Идея → Предположения → Эксперименты | Нужно найти проблему «в жизни пользователя» |
| От гипотез | Идея → Продуктовая гипотеза → Эксперименты | Идея уже есть, нужно проверить |
| От трендов | Тренд → Возможность → Концепция → Pre-mortem | Задание «от тренда / технологии» |
| Проверка концепции | Pre-mortem → Сценарии «что если» → MVP-доска | Концепция выбрана, нужно её «пробить» |

**Тип карточки «Продуктовая гипотеза»** (из текста, с условным полем):
- Если мы… (`longtext`, обязательное);
- То пользователи… (`longtext`, обязательное);
- Ожидаемое изменение (`percent`);
- Уверенность (`select`: низкая / средняя / высокая);
- Основание (`select`: опыт / наблюдение / данные / догадка);
- Источник (`link`, показывается, если основание = данные);
- Как проверим? (`longtext`).

## 4. Механики

### 4.1. Паспорт задания (идея 2)

**Что это:** экран проекта, который организатор заполняет до начала, за 3–5 минут.
Можно вставить текст задания от преподавателя целиком в поле «Исходный текст».
Остальные поля необязательные.

| Поле | Тип |
|---|---|
| Что нужно получить | текст |
| Какую задачу решаем | текст |
| Для кого | текст (подставляется в «Кто сталкивается») |
| Ограничения | список строк |
| Обязательно в результате | список строк |
| Нельзя или нежелательно | список строк |
| Сколько времени | выбор сценария времени |
| Как оценит преподаватель | список строк |

**Как используется:**
1. **Виден всем всегда.** Кнопка «📋 Задание» в верхней панели у участника и
   организатора, а в лобби паспорт показан крупно.
2. **Ограничения → критерии в один клик.** На шаге «Критерии» у каждого ограничения
   есть кнопка «Сделать критерием» → создаётся критерий «Соответствие: <ограничение>»
   с описаниями 1 = нарушает, 3 = частично, 5 = полностью выполняет.
3. **Проверка соответствия на шаге «Решение».** По выбранной карточке организатор
   отмечает пункты «Обязательно» и «Нельзя»: ✅ / ⚠️ / ❌. Если есть ❌, появляется
   предупреждение «Выбранное противоречит заданию: …». В итог и экспорт идёт таблица
   соответствия.
4. **Критерии преподавателя** показываются в итоге рядом с результатом: удобно для
   самопроверки перед сдачей.

### 4.2. Реестр предположений и эксперименты (идеи 5 и 6)

**Предположение** — объект проекта, а не этапа: живёт через все этапы.

| Поле | Значение |
|---|---|
| Формулировка | «Студенты готовы платить 199 ₽/мес» |
| Связано с | карточка (идея, проблема, гипотеза) |
| Категория | Желательность (нужно ли людям) / Реализуемость (сможем ли сделать) / Жизнеспособность (окупится ли) |
| Важность | 1–5: насколько концепция рушится, если это неверно |
| Доказанность | 1–5: насколько это уже подтверждено |
| Статус | не проверено / проверяется / подтверждено / частично / опровергнуто / мало данных |
| Доказательство | текст + ссылка |
| Автор | скрыт при анонимности |

**Откуда берутся предположения** (тут сервис помогает, а не только хранит):
- карточки с основанием «Догадка» — кнопка «Записать как предположение»: формулировка
  берётся из карточки, статус «не проверено»;
- значок 🎲 «На догадках» в результатах ведёт сюда же;
- причины из pre-mortem — «Скрытое предположение: …»;
- вручную, в любой момент сессии, любой участник.

**Шаг «Карта предположений»** — новый шаг режима `decide` на 5–10 минут:
1. Участники вслепую оценивают важность (1–5) и доказанность (1–5). Это то же ядро
   слепой оценки с двумя фиксированными критериями.
2. Результат — матрица 2×2 «важность × доказанность». Верхняя левая четверть
   (важно, но не доказано) — **«прыжок веры»: проверять первым**. Эту схему
   предлагает Дэвид Бланд в Assumption Mapping.
3. Спорные оценки (⚡) работают как обычно: разброс — повод обсудить.

**Зависимости.** У выбранной концепции есть список «держится на предположениях».
Если любое из них переходит в «опровергнуто», концепция получает значок
«⛔ Под угрозой: опровергнуто „…“». Если в «прыжке веры» больше трёх
непроверенных, появляется подсказка «концепция держится на непроверенном».

**Эксперимент** (тест-карточка) — проверяет предположение:

| Поле | Пример |
|---|---|
| Проверяем | ссылка на предположение (формулировка подставляется) |
| Метод | опрос / интервью / лендинг / прототип / наблюдение / анализ конкурентов |
| Кого и сколько | «студенты 1–2 курса», N = 30 |
| Метрика | «доля, кто сталкивался за последний месяц» |
| Порог успеха | ≥ 40% (или ≥ 12 из 30) |
| Срок, ответственный | дата, участник |
| Факт | 14 из 30 |
| Вывод | авто: 47% ≥ 40% → «подтверждено» (можно поправить вручную с причиной) |

**Автоматический вердикт:**
- факт ≥ порога → «подтверждено»;
- от 75% до 100% порога → «частично»;
- меньше 75% порога → «опровергнуто»;
- N меньше запланированного вдвое → «мало данных».

Вердикт переносится в статус предположения. Порог в 75% выбран как простое
понятное правило, его можно настроить.

**Честная подсказка о выборке:** рядом с N показываем примерную погрешность доли
`±98/√N` процентных пунктов (95%). Например, «при 30 ответах погрешность около
±18 п.п. — 47% и 40% статистически не различимы». Это учит не переоценивать маленький
опрос, но не требует знания статистики.

### 4.3. Развитие идей и генеалогия (идея 3)

**Новый необязательный шаг «Развитие»** — между «Тихой генерацией» и «Склейкой»,
5–10 минут. По логике это 1-2-4-All: сначала каждый сам, потом работа с чужими идеями.

1. Каждый участник получает **2 чужие карточки, назначенные по кругу**. Свои не
   попадаются, каждая карточка достаётся двум разным людям. Это не даёт всем развивать
   одну «громкую» идею — тот же эффект якорения, от которого защищает слепая оценка.
2. Действия над карточкой:
   - **«Развить»** — создаётся новая карточка, поля копируются из исходной, её можно
     изменить, ставится связь «развитие №3»;
   - **«Объединить с…»** — новая карточка из двух, связь «сочетание №3 + №5»;
   - **«Пропустить»**.
3. Исходные карточки остаются. В оценку идут все: ранние, развитые и объединённые.
   Новые версии часто оказываются сильнее — это и проверяем.

**Данные:** у карточки появляется `parents: [{id, kind: 'develop' | 'combine'}]`.
Отдельной истории версий нет: каждая версия — самостоятельная карточка. Возврат
к версии — это просто выбор исходной карточки.

**Дерево происхождения** в результатах и итоге: узлы — карточки с баллами, стрелки —
связи. Сразу видно, что «победитель — сочетание №2 и №5». При анонимности в узлах
номера, а не авторы.

**Сравнение версий:** для пары «исходная → развитая» поля показываются рядом, изменённые
слова подсвечены (простое сравнение по словам).

### 4.4. Склейка остаётся
Склейка («это одно и то же») и развитие («это новое на основе того») — разные действия.
Склейку оставляем как есть. В дереве склеенные карточки показываются одним узлом
с пометкой «склеено из 3».

### 4.5. Pre-mortem (идея 7)

Готовый сценарий на базе режима `decide`, без нового кода движка:

- **Тип карточки «Причина провала»:**
  - Что пошло не так (обязательное);
  - Категория: проблема оказалась незначительной / люди не стали менять привычки /
    ресурсы / технология / конкурент / деньги / другое;
  - Ранний сигнал: что мы заметили бы заранее.
- **Подсказка шага:** «Прошло 6 месяцев. Наш продукт закрылся. Почему?». Формулировку
  «уже случилось» рекомендует автор метода Гэри Кляйн (HBR, 2007).
- **Критерии по умолчанию:** «Вероятность» и «Ущерб».
- **Матрица** по умолчанию «вероятность × ущерб», значок «🔥 Критический риск» —
  оба среднего ≥ 3,5.
- **Шаг «Решение»** вместо «выбрать» предлагает «меры»: у каждого критического риска
  поле «Как предотвратим» и, по желанию, «Создать предположение» или «Создать
  эксперимент».
- **Результат** — реестр рисков проекта, он попадает в итог и экспорт.

### 4.6. Карта пользовательского пути (идея 4)

Новый режим этапа `journey`, 20–30 минут:

1. **Персона и сценарий.** Организатор пишет одну строку из паспорта, например
   «Первокурсник готовится к первой сессии».
2. **Шаги пути.** Участники предлагают шаги (как сейчас критерии), организатор
   утверждает и упорядочивает 4–7 шагов перетаскиванием.
3. **Тихое заполнение.** Каждый по каждому шагу добавляет:
   - барьеры (короткие карточки «что мешает»);
   - эмоцию: 5 смайлов от 😣 до 😄, это шкала −2…+2.
4. **Кривая эмоций.** Средние эмоции по шагам показываются линией, разброс — полосой.
   Самые «низкие» шаги видны сразу.
5. **Голосование.** Голосование одобрением (как наш «Отбор»): «самые болезненные
   барьеры», до 3 отметок на человека.
6. **«Сделать проблемой».** Топ-барьеры одним нажатием превращаются в карточки
   проблем следующего этапа:
   - кто = персона;
   - в какой ситуации = шаг пути;
   - что мешает = барьер.

Так команда не придумывает абстрактную проблему, а находит её в конкретном моменте
жизни пользователя. Это и есть ценность карты пути, о которой говорит текст.

### 4.7. Сценарии «что если» (идея 8)

Работает поверх результатов любого этапа `decide`, 5–10 минут:

1. Организатор создаёт сценарий: название («Бюджет урезали вдвое»), описание и одно
   из двух изменений:
   - **сдвиг весов:** например, «Реализуемость» ×3;
   - **условие-проверка:** финалисты получают вопрос «Выдерживает ли условие?»
     ✅ / ⚠️ / ❌, на который все отвечают вслепую.
2. **Пересчёт без новых оценок.** Для сдвига весов рейтинг считается из уже собранных
   оценок, математика та же. Условие-проверка добавляет множитель:
   ✅ = 1, ⚠️ = 0,7, ❌ = 0,3 (по большинству ответов).
3. **Экран «Устойчивость».** Таблица «карточка × сценарии» с местами и баллами. Итоговый
   вывод: «№2 первая в 3 из 4 сценариев — самая устойчивая; №1 лидирует только при
   исходных условиях».

Это развитие уже существующей проверки «устойчивость лидера»: теперь организатор сам
задаёт, относительно чего проверять устойчивость.

### 4.8. MVP-доска (идея 9, частично)

Новый режим этапа `board`, 15–25 минут, для выбранной концепции:

1. **Компоненты.** Участники добавляют компоненты:
   - название;
   - тип: функция / интерфейс / данные / интеграция / внешний участник;
   - «зависит от» (`cardref`).
2. **Слепая оценка** «Ценность» и «Сложность» — то же ядро оценки.
3. **Автоматическая раскладка-подсказка:** высокая ценность и низкая сложность →
   кандидат в MVP. Организатор раскладывает компоненты по корзинам
   **MVP / Версия 2.0 / Потом** перетаскиванием.
4. **Проверки:**
   - компонент из MVP зависит от компонента не из MVP → «⚠️ MVP не соберётся без „…“»;
   - суммарная сложность MVP больше бюджета → «MVP слишком большой, урежьте».
     Бюджет — в очках из паспорта, по умолчанию 10.
5. **Итог:** список MVP с зависимостями, текстом для отчёта и для Lean Canvas
   («Решение», «Ключевые метрики»).

**Не делаем:** схему архитектуры с «техническими зависимостями» на холсте — это работа
на часы и не для телефона.

### 4.9. Ресурсы (идея 10, минимум)

Полный планировщик (часы, навыки, перенос задач, план и факт) — это отдельный продукт,
и на паре он не нужен. Оставляем то, что закрывает основную боль «кто и что делает
к следующему занятию»:
- у каждого эксперимента и меры против риска есть **ответственный и срок**;
- вид «**Кто что делает**»: по каждому участнику его эксперименты и меры, сроки и
  статусы. Если у человека больше трёх открытых задач, он отмечен «⚠️ перегружен»;
- экспорт этого списка в Markdown для чата команды. Так задачи переживают время
  между занятиями, пока ноутбук закрыт.

## 5. Изменения в модели данных

```ts
// Шаблоны
type FieldType = 'text' | 'longtext' | 'number' | 'percent' | 'select' | 'multiselect'
               | 'checkbox' | 'date' | 'scale' | 'link' | 'cardref'
interface FieldDef {
  key: string; label: string; hint?: string; type: FieldType; required: boolean
  options?: string[]; min?: number; max?: number; maxLength?: number
  showIf?: {field: string; equals?: string; in?: string[]; notEmpty?: boolean}
  prefill?: string            // 'source.<key>'
}
interface CardType { id: string; name: string; fields: FieldDef[]; titleField: string; subtitleFields: string[]; lint: string[] }
type StageMode = 'decide' | 'journey' | 'board'
interface StageTemplate {
  id: string; name: string; emoji: string; mode: StageMode; cardType: CardType
  defaultCriteria: string[]   // ключи библиотеки
  optionalSteps: ('evolve' | 'assumptionMap' | 'scenarios')[]
  intro: Partial<Record<Phase, string>>
  matrixAxes?: [string, string]
  builtin?: boolean
}
interface Workflow { id: string; name: string; steps: string[] /* id шаблонов */ }

// Значения полей становятся типизированными
type FieldValue = string | number | boolean | string[] | null
Card.fields: Record<string, FieldValue>
Card.parents?: {id: string; kind: 'develop' | 'combine'}[]
Card.stepId?: string          // режим journey
Card.bucket?: 'mvp' | 'v2' | 'later'   // режим board
Card.deps?: string[]

// Этап хранит копию шаблона
Stage.template: StageTemplate      // Stage.type остаётся для старых проектов
Stage.scenarios?: Scenario[]
Stage.journey?: {persona: string; steps: {id: string; title: string; order: number}[]; emotions: {raterId: string; stepId: string; value: -2|-1|0|1|2}[]}

// Проект
Project.passport?: Passport
Project.assumptions: Assumption[]
Project.experiments: Experiment[]
Project.risks: Risk[]
Project.workflowId?: string
```

**Миграция старых проектов:** при открытии `stage.template ??= BUILTIN[stage.type]`.
Строковые поля и так валидные значения `FieldValue`. Тест миграции на реальном файле
проекта обязателен.

**Хранилище шаблонов:** отдельное хранилище `templates` в IndexedDB, импорт и экспорт `.json`.

## 6. Изменения в протоколе и движке

- **Новые действия:**
  - `passport.update`;
  - `assumption.upsert / delete / rate`;
  - `experiment.upsert / result`;
  - `card.develop / combine`;
  - `journey.step.* / emotion.set`;
  - `board.move`;
  - `scenario.upsert / answer`;
  - `compliance.set`.
- **Права:**
  - реестры может пополнять любой участник;
  - править и удалять — автор и организатор;
  - менять паспорт, шаблон и сценарии — только организатор.
- **Проектные данные** (паспорт и реестры) рассылаются отдельным сообщением
  `{k: 'project', v, version}` и только при изменении, а не каждые 12 секунд вместе
  с состоянием этапа. Так основное сообщение остаётся маленьким.
- **Размер:** держим общее состояние этапа меньше 40 КБ после сжатия. При больших
  реестрах рассылаем только изменения. Оценка: 50 предположений по 300 байт ≈ 15 КБ
  до сжатия — запас есть.
- **Проверка значений полей** — в движке по `FieldDef`: тип, обязательность с учётом
  `showIf`, варианты, длина. Проверка в интерфейсе повторяет ту же функцию: один код
  на обе стороны.
- **Слепота** для новых оценок (важность и доказанность предположений, ценность и
  сложность компонентов, ответы «выдерживает ли условие») — тем же механизмом: до
  раскрытия только прогресс.

## 7. Интерфейс: как не перегрузить

- **Новый проект:** 3 шага.
  1. Паспорт: можно пропустить или вставить текст задания.
  2. Сценарий: карточки встроенных сценариев с описанием «когда подходит»
     и пункт «Собрать свой».
  3. Время и режим (телефоны или один экран).
- **Конструктор** — только в «Собрать свой» и «Настроить шаблон этапа».
- **У участника ничего нового, кроме кнопки «📋 Задание» и новых видов шагов.**
  Каждый шаг по-прежнему одна короткая подсказка и одно действие.
- **У организатора** появляется вкладка «Проект»:
  - паспорт;
  - предположения;
  - эксперименты;
  - риски;
  - «Кто что делает»;
  - дерево идей.

## 8. Тестирование

- **Модульные тесты:**
  - проверка полей всех типов и `showIf`;
  - вердикт эксперимента на крайних значениях;
  - погрешность выборки;
  - пересчёт сценариев (веса и множители);
  - проверка зависимостей MVP;
  - распределение «2 чужие карточки по кругу» (своих нет, у каждой карточки два
    человека, при 2–8 участниках);
  - миграция старого файла проекта.
- **Протокол:** новые действия при потере 30% сообщений, отдельная рассылка проектных
  данных, права.
- **Сквозной сценарий в браузере:** «Sprint-lite» целиком (карта пути → проблема →
  идея → предположения → эксперимент) с организатором и двумя телефонами.
- **Полевой тест:** одно занятие на «Классике» с паспортом и одно на «Sprint-lite».

## 9. План внедрения

Порядок задан зависимостями: конструктор нужен всем остальным. Затем идёт то, что даёт
больше пользы за меньший объём. Каждый этап заканчивается контрольной точкой — вашей
проверкой.

| Этап | Что входит | Зависит от | Готово, когда |
|---|---|---|---|
| **A. Конструктор** | Шаблоны, 11 типов полей, обязательные и условные поля, подстановка из предыдущего этапа, редактор с предпросмотром, «Мои шаблоны», импорт и экспорт, сценарии-цепочки, миграция | — | «Проблема → Идея» работает как сейчас, но через шаблоны; собранная с нуля «Продуктовая гипотеза» проходит полный цикл; старый проект открывается без потерь |
| **B. Паспорт задания** | Экран паспорта, кнопка «📋 Задание», ограничения → критерии, проверка соответствия в решении и итоге | A | Нарушение обязательного условия видно на шаге «Решение» и в экспорте |
| **C. Предположения и эксперименты** | Реестр, «Записать как предположение» из 🎲, шаг «Карта предположений» (2×2), зависимости концепции, тест-карточка, авто-вердикт, погрешность, ответственный и срок | A | Сквозная цепочка «догадка → предположение → эксперимент → факт → статус → значок у концепции» работает |
| **D. Развитие идей** | Шаг «Развитие», назначение по кругу, «развить» и «объединить», `parents`, дерево, сравнение версий | A | В дереве видно происхождение победителя; при анонимности авторство не вычисляется |
| **E. Pre-mortem** | Встроенный сценарий, матрица рисков, «меры», реестр рисков | A, C | Pre-mortem проходит за 15 минут, критические риски уходят в предположения и эксперименты |
| **F. Карта пути** | Режим `journey`, кривая эмоций, голосование, «Сделать проблемой» | A | Барьеры с карты становятся карточками следующего этапа |
| **G. Сценарии «что если»** | Сдвиг весов, условие-проверка, экран устойчивости | — (ядро) | Видно, какая карточка устойчива при изменённых условиях |
| **H. MVP-доска** | Режим `board`, корзины, проверка зависимостей и бюджета | A | Нарушенная зависимость MVP подсвечена, список MVP в экспорте |
| **I. «Кто что делает»** | Вид по участникам, экспорт в Markdown | C, E | Список задач к следующему занятию копируется в чат одной кнопкой |

**Почему реестр (C) раньше генеалогии (D),** хотя в тексте наоборот: C связывается
с уже работающим значком 🎲 и с паспортом и даёт эффект сразу, на ближайшем занятии.
D ценна, но добавляет к сессии ещё 5–10 минут, а это не всегда возможно.
